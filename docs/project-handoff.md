## Bot API: рабочая конфигурация
- **Хост: `platform-api.max.ru`** (переопределяется `MAX_API_HOST`). Документация
  рекомендует `platform-api2.max.ru`, но его сертификат выпущен «Russian Trusted
  Sub CA» (Минцифры) и не проходит проверку с dev-машины. На проде с установленным
  корнем Минцифры можно переключиться на api2.
- Токен — **заголовком `Authorization`**; параметр URL `access_token` отвергается
  с `verify.token`.
- Лимит: 30 rps на всё API бота; при 429 читать `Retry-After`.

  - подписан → **200 + запись в members**;

## Gating (backend/src/subscription.js)
- `SUBSCRIPTION_GATING`: `off` (по умолчанию) / `shadow` (решение логируется,
  никто не блокируется) / `on` (not_subscribed → 403, ошибка → fail-open).
- Кэш: subscribed 15 мин, not_subscribed 60 сек, error не кэшируется; после 429 —
  backoff по Retry-After.
- Интерлок: `on` требует `STRICT_INIT_DATA=on`, иначе сервер не стартует —
  без подписи initData userId подделывается заголовком.
- Старт-проверка `GET /chats/{id}`: не 200 или type≠channel → громкая ошибка в лог
  (неверный chatId при fail-open молча открыл бы доступ всем).
- **Текущее состояние (29.08.2026): shadow включён через backend/.env** и переживает
  перезапуски. Ждём в логах строку `decision: not_subscribed` от РЕАЛЬНОГО
  пользователя — это последний непроверенный факт перед включением on
  (тесты гонялись на несуществующем id, живой неподписанный аккаунт не попадался).

## MAX Bridge / initData (webapp + middleware, проверено ранее)
- Скрипт st.max.ru/js/max-web-app.js создаёт window.WebApp ДАЖЕ вне MAX —
  признак настоящего клиента только непустой initData (фронт так и определяет режим).
- Подпись initData: secret = HMAC-SHA256("WebAppData", MAX_BOT_TOKEN), затем подпись
  отсортированных a→z параметров, склеенных \n. Сверено с реальной строкой с телефона.
- STRICT_INIT_DATA (off по умолчанию): on → 401 без валидной/свежей подписи.
  Локальные запросы отличаются НЕ по адресу (ngrok проксирует на 127.0.0.1),
  а по отсутствию X-Forwarded-For.

## Misread-детектор (backend/src/services/misread.js)
- Флаг MISREAD_DETECTION (сейчас on в .env, лог-only): после vision, параллельно
  solveTask, fire-and-forget — пользователь не ждёт. Числовые цепочки равенств
  из работы ученика сверяются через verify_sympy (числа в Rational — иначе
  python-float даёт ложные 10⁻¹³-расхождения).
- ДВА ограничения по построению: (1) видит только числовые равенства — переменные,
  неравенства, столбики-аннотации мимо; (2) слеп к систематической подмене:
  ловит misread, только когда тот ЛОМАЕТ соотношение. «1,38→1,58 везде + итог 158»
  не поймался бы; ma-02 пойман из-за ВТОРОЙ ошибки (37,5→57,5 сломало сумму =100).
- Флаг НЕ различает misread и настоящую ошибку ученика — показывать пользователю
  как «ошибка распознавания» нельзя. Числа никогда не исправляются.
- Стоимость: по одному SymPy-процессу на пару, последовательно, в фоне
  (13 пар ma-07 = 13 процессов по ~0.25 с; пользователь не ждёт).

## Замер Opus vs Haiku на solver (30.08.2026, инструмент model-compare)

  Haiku шла с фиксированным бюджетом мышления 8000 вместо adaptive
  (модель до 4.6 не умеет adaptive/effort) — это шим инструмента.
- Вся разница — дисциплина формата finalAnswer (Haiku пишет «1/2 (или 0,5)»,
  LaTeX) и трактовка границ программы, а не правильность.
- **НЕ проверено**: многошаговые задачи — вторая часть ОГЭ/ЕГЭ, геометрия
