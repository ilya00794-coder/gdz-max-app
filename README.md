# Решебник для MAX

Мини-приложение в мессенджере MAX: ученик фотографирует задачу или домашнюю работу —
приложение решает или проверяет её.

## Структура
- `webapp/` — фронтенд мини-приложения (открывать `webapp/index.html` для локального превью UI)
- `backend/` — API-сервер (Node.js/Express, пока с мок-логикой)
- `docs/` — архитектура, бэклог
- `CLAUDE.md` — контекст проекта для Claude Code, читать в первую очередь

## Быстрый старт (backend)
```bash
cd backend
npm install
python3 -m pip install -r requirements.txt --user   # sympy, нужен для верификации ответов

# Postgres для кэша решений
brew install postgresql@16
brew services start postgresql@16
createdb gdz_max

cp .env.example .env   # и вписать реальный ANTHROPIC_API_KEY
npm run migrate        # создать таблицу solutions_cache
npm run dev            # подхватывает .env; `npm start` — без него
```

**Нужен `python3` с установленным `sympy`** — на нём работает символьная проверка ответов
(`backend/src/services/verify.js` запускает `verify_sympy.py` отдельным процессом).
Если pip ругается на externally-managed environment (Homebrew/системный Python на новых ОС),
используйте `python3 -m pip install -r requirements.txt --break-system-packages`.
Проверить: `python3 -c "import sympy; print(sympy.__version__)"`.
Без sympy сервер работает, но верификация возвращает `method: "sympy_unavailable"`,
и такие решения не попадают в кэш.
Сервер поднимется на `http://localhost:3000`.

Без `ANTHROPIC_API_KEY` сервер запустится, но эндпоинты с фото вернут `503`
с понятным сообщением — это ожидаемое поведение.

## Быстрый старт (webapp)
Просто открыть `webapp/index.html` в браузере для превью UI. Вне клиента MAX объект
`window.WebApp` не появится, приложение это переживает и работает в режиме превью.

## Тест внутри MAX через ngrok

Мини-приложение внутри MAX открывается по HTTPS, поэтому и статика, и бэкенд должны быть
доступны по HTTPS. Локально это делается двумя туннелями.

```bash
# один раз: токен из https://dashboard.ngrok.com/get-started/your-authtoken
ngrok config add-authtoken <ваш-токен>

# терминал 1 — бэкенд
cd backend && npm run dev

# терминал 2 — статика мини-приложения
cd webapp && npx serve -l 5500

# терминал 3 — туннель на бэкенд
ngrok http 3000

# терминал 4 — туннель на статику
ngrok http 5500
```

Дальше:

1. Взять https-адрес туннеля бэкенда и вписать его в `webapp/config.js`:
   ```js
   window.APP_CONFIG = { BACKEND_URL: "https://<адрес-туннеля-3000>.ngrok-free.app" };
   ```
   Это единственное место, где задаётся адрес API — основной код править не нужно.
2. Https-адрес туннеля статики (порт 5500) указать как URL мини-приложения
   в настройках бота на business.max.ru.

Бесплатный тариф ngrok держит **один** туннель одновременно: для двух понадобится платный
план либо второй способ отдать статику по HTTPS (GitHub Pages, любой статический хостинг).

## Строка запуска MAX (initData)

Мини-приложение передаёт подписанную строку запуска заголовком `X-Max-Init-Data`.
На бэкенде её разбирает `backend/src/middleware/maxInitData.js`: раскладывает параметры,
достаёт `userId`, считает возраст `auth_date` и статус подписи, кладёт всё в `req.max`
и пишет в лог.

Сейчас это **наблюдатель**: запросы не отвергаются ни при каком статусе. Проверка подписи
уже реализована (`secret_key = HMAC-SHA256("WebAppData", MAX_BOT_TOKEN)`, затем подпись
отсортированных по ключу параметров), но без `MAX_BOT_TOKEN` в окружении статус будет
`no_token`. Включение строгого режима — отдельный шаг.

В лог не пишутся ни имя пользователя, ни телефон, ни содержимое чата — только перечень
пришедших полей, `userId` и статус подписи.

## Данные школьной программы (справочный слой для solver.js)

`backend/src/data/curriculum/math.json` — структурированная программа по математике
1–11 классов: какие темы и какие **способы решения** ученик уже прошёл к конкретному
моменту. Нужно, чтобы решение объяснялось методом, доступным ученику (шестикласснику —
не через дискриминант).

Доступ к данным — через `backend/src/services/curriculum.js`:

```js
import { getAllowedMethods } from "./src/services/curriculum.js";

getAllowedMethods({ grade: 6, subject: "Математика" });             // за весь 6 класс
getAllowedMethods({ grade: 8, subject: "Алгебра", quarter: 2 });    // ещё без дискриминанта
```

Этот список подключён к `backend/src/services/solver.js`: он уходит в системный промпт как
белый список («решай только этими методами»), а `POST /api/solve` принимает необязательный
`quarter`. В ответе есть `usedMethods` — какими методами модель воспользовалась,
и `programWarning` — если задачу нельзя решить пройденным материалом.

### Источники

Только официальные федеральные рабочие программы (ФРП) с портала «Единое содержание
общего образования» Минпросвещения. Программы издательств и авторов учебников
(Виленкин, Мерзляк, Атанасян и др.) и тексты учебников **не использовались**.

- ФРП «Математика», 1–4 классы — https://edsoo.ru/wp-content/uploads/2025/07/2025_noo_frp_matematika_1-4.pdf
- ФРП «Математика», 5–9 классы, базовый уровень — https://edsoo.ru/wp-content/uploads/2025/07/2025_ooo_frp_matematika-5-9_baza.pdf
- ФРП «Математика», 10–11 классы, базовый уровень — https://edsoo.ru/wp-content/uploads/2025/07/2025_soo_frp_matematika_10_11_baz.pdf
- Раздел портала со всеми программами — https://edsoo.ru/rabochie-programmy/

Разбор по документам, метод расчёта четвертей и его ограничения —
`backend/src/data/curriculum/SOURCES.md`. Главное ограничение: **ФРП не делит программу
на четверти**, поле `quarter` — наша расчётная оценка по часам из тематического
планирования, а не цитата из документа.


## Кэш решений (Postgres)

Проверенные решения лежат в таблице `solutions_cache` базы `gdz_max`, чтобы не платить
за повторное решение одной и той же задачи. Подключение — через `DATABASE_URL`
(по умолчанию `postgresql://localhost/gdz_max`), драйвер `pg`, без ORM.

- Ключ строит `buildCacheKey` — чистая функция, к базе не обращается: `book:<учебник>:<класс>:<предмет>:<номер>`,
  если номер задания распознан на фото, иначе `text:<хэш условия>`.
- В кэш попадают **только** решения с `verification.verified === true` (см. `routes/solve.js`).
- Колонка `verification_method` дублирует метод проверки отдельно от `jsonb` — чтобы
  eval-дашборд мог выбрать «все решения, проверенные через sympy» без разбора JSON.
- Хранятся только НАШИ собственные решения. Ни текстов чужих решебников, ни страниц
  учебников, ни фотографий пользователей в базе нет.

Схема — `backend/src/db/schema.sql`, миграция — `npm run migrate`. Миграция запускается
**вручную** и идемпотентна (`CREATE TABLE/INDEX IF NOT EXISTS`); автоматически при старте
сервера она не выполняется — изменение схемы должно быть осознанным действием.

**Если база недоступна, сервер не стартует** и печатает, что именно чинить. Тихого отката
на in-memory нет намеренно: он замаскировал бы поломку кэша ровно тогда, когда мы уверены,
что кэш уже работает через базу.

## Верификация ответов (SymPy)

Финальный ответ решателя проверяется символьно, а не «на глаз»: `solver.js` возвращает
`formalExpression` (например `solve(Eq(2*x + 8, 20), x)`), `verify.js` решает эту задачу
через SymPy и сравнивает множество корней с ответом. Сверяется **только финальный ответ** —
он не защищён авторским правом, в отличие от текста объяснения.

- Сравниваются **действительные** корни: школьный ответ по умолчанию вещественный,
  комплексные корни в него не выносятся.
- Ответ разбирается терпимо к человеческому формату: юникод-минус `−`, десятичная запятая,
  индексы `x₁`, «корней нет» как пустое множество.
- В кэш попадают **только** решения с `verified: true` (см. `routes/solve.js`).
- Если SymPy не смог разобрать запись или предмет не проверяется символьно —
  `verified: false, method: "unsupported"`. Никаких догадок.

Безопасность: `formalExpression` генерирует LLM, поэтому строка не выполняется как есть.
Два рубежа — белый список символов и имён в `verify.js` и разбор в AST с белым списком узлов
и функций в `verify_sympy.py`; вычисление идёт в отдельном процессе, без builtins,
с таймаутом (`VERIFY_TIMEOUT_MS`, по умолчанию 5 с).

## Проверка домашней работы (`POST /api/check-homework`)

Поток из пяти шагов:

1. **vision**, режим `studentWork` — расшифровываем тетрадь как есть, вместе с ошибками
   ученика: исправлять их на этом этапе нельзя, иначе проверять будет нечего.
2. **solver** — независимо решаем ту же задачу с учётом программы класса, получаем эталон.
   Эталон — наше собственное решение, а не текст из чужого решебника.
3. **compare** (`services/compare.js`) — отдельный вызов Claude API сравнивает ход решения
   по шагам и находит ПЕРВЫЙ ошибочный шаг. SymPy тут не годится: символьная алгебра умеет
   сверить ответ, но не умеет прочитать ход мысли.
4. **verify** — SymPy объективно проверяет финальный ответ ученика по формализации из эталона.
5. **сверка вердиктов** (`crossCheckVerdicts`) — если пошаговый разбор и SymPy расходятся,
   это не «выбери, кому верить»: расхождение логируется, а наружу отдаются оба вердикта
   в поле `verdictConflict`. Спорим только когда SymPy реально посчитал — `method: "unsupported"`
   означает «проверить не смогли», а не «ответ неверен».

Что модель НЕ считает ошибкой: другой (но верный) способ решения, оформление, почерк,
отсутствие «Ответ:», а также фрагменты, закрытые рукой или не распознанные — они уходят
в `unreadableFragments`. Отсутствие данных не доказательство ошибки.

**Разделение для UI:** «вот твоя ошибка» и «вот как правильно» лежат в разных полях ответа.
`comparison.mistakes[]` — где ошибся ученик (внутри каждой ошибки `whatStudentDid` и
`whatShouldBeDone` тоже разведены по разным полям), `referenceSolution` — эталонное решение
целиком. Смешивать их на одном экране не нужно: ученик должен сначала увидеть свою ошибку.
