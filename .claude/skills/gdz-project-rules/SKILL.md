# Правила точности и источников контента для решебника

## Жёсткое ограничение (не пересматривать без явного обсуждения с пользователем)
Никогда не предлагай и не реализуй:
- скачивание/парсинг текстов чужих готовых решебников (ГДЗ) или учебников для использования в базе ответов или как обучающих данных;
- обучение/дообучение модели на текстах чужих ГДЗ так, чтобы она воспроизводила похожий текст;
- хранение отсканированных страниц учебников целиком.

Это не техническое ограничение "пока не сделали", а сознательное решение проекта из-за
авторского права. Финальный числовой/фактический ответ не защищён авторским правом — его
можно использовать как эталон при сверке. Конкретный текст объяснения — защищён, копировать нельзя.

## Как достигать точности вместо этого
1. Решение генерируется "с нуля" через Claude API, с учётом класса ученика (методы, пройденные
   по программе на данный момент).
2. Верификация финального ответа: Wolfram Alpha / SymPy для точных наук; сверка с купленными
   ГДЗ или ручной проверкой эксперта — только финальный ответ, не текст объяснения.
3. Кэш верифицированных решений по каноническому ключу (учебник+номер, либо хэш условия) —
   см. cache.js.
4. При расхождении система/эталон — логировать, не пытаться "угадать" правильный ответ,
   не показывать пользователю неверифицированное решение как финальное без пометки.

## Проверка перед коммитом
Перед тем как считать задачу выполненной, убедись, что:
- новый код не содержит захардкоженных текстов из внешних источников решебников;
- любые "эталонные" данные, которые появляются в коде/тестах, помечены как собственные
  примеры проекта, а не скопированы с внешнего сайта.

## Обязательный процесс для КАЖДОГО изменения

### 1. Перед изменением — анализ зависимостей
Прежде чем писать код, найди и перечисли ВСЕ места, которые зависят от того, что меняешь:
- Кто вызывает функцию/роут, который правишь? (grep по имени)
- Какие поля ответа/схемы читают другие модули? Если добавляешь/меняешь поле — кто его потребляет?
- Меняешь backend — какие места фронта это затрагивает, и наоборот?
- Меняешь схему БД — не заденет ли существующие таблицы/данные?
- Есть ли общий код (postJson, humanizeError, cache, verify), который тоже нужно учесть?
Явно напиши пользователю: «это изменение затрагивает также X, Y, Z» — ДО реализации.

Порог. Полный анализ обязателен, когда меняется:
- схема или поля ответа API;
- сигнатура функции, которую вызывают другие модули;
- схема БД;
- общий код (postJson, humanizeError, cache, verify и т.п.);
- либо правка идёт и на backend, и на фронте одновременно.
Для правок в пределах ОДНОГО файла, не меняющих публичный интерфейс (сигнатуры, схемы
ответов, поля БД), полный разбор не нужен — достаточно короткой проверки «наружу это
никого не задевает» и одной строки об этом в отчёте.

### 2. Предполагай смежную работу
Не делай буквально только то, что попросили, если очевидно, что без смежной правки фича
сломается или будет неполной. Назови смежные вещи и предложи, но не делай их молча без
согласия — покажи, что заметил, и спроси/предложи.

### 3. После КАЖДОГО изменения — канарейка (обязательно)
Никогда не считай задачу выполненной без проверки. После изменения ВСЕГДА:
- прогони конкретный тест, доказывающий, что изменение работает (не «должно работать», а
  реальный прогон: curl / headless / запуск сервера);
- прогони проверку, что НЕ сломалось смежное (регрессия): особенно то, что нашёл на шаге 1;
- если тест показал странность — не списывай на случайность, разберись, почему (частая
  причина — врёт сам тест/мок, а не продукт);
- покажи пользователю результаты канарейки, а не только сообщение «готово».
Канарейка бывает частичной, и это нормально — ненормально выдавать её за полную:
- что можно проверить автоматически — проверяй и показывай результат прогона;
- что физически нельзя (тач-жесты, нативное меню выбора фото, реальный MAX-initData,
  поведение на проде) — назови явно, пометь канарейку как ЧАСТИЧНУЮ и напиши, что именно
  пользователь должен проверить на телефоне;
- непроверяемое не выдавай за проверенное ни формулировкой, ни умолчанием.

### 4. Честность в отчёте
- Явно говори, что проверено, а что нет.
- Не выдавай непроверенное за проверенное.
- Если по дороге поймал баг или сомнительное место — назови его, даже если не просили.

## Механики MAX, проверенные на практике
- Очередь событий Bot API переживает отсутствие приёмника: событие bot_added
  забралось long-polling'ом задним числом, спустя часы, действий на телефоне
  не потребовалось. Прежде чем просить пользователя что-то дёргать в MAX —
  сначала опроси /updates: нужное событие может уже лежать в очереди.
- Хост platform-api.max.ru (не api2 — сертификат Минцифры), токен только
  заголовком Authorization. Подробности: docs/project-handoff.md.
